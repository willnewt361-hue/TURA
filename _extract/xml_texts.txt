1. Executive brief
TURA is an offline-first bus-booking and operations system. The first version should run locally without Mobile Money APIs, while keeping a clean integration boundary so MTN/Airtel payments can be connected later. The browser UI is HTML5/CSS/JavaScript, the backend is Python, and WebSockets carry live seat, trip, tracking, driver, ticket and SOS events.
The practical target for today is a polished working prototype, not a production payment deployment.

2. Non-negotiable product rules
Do not hard-code payment-provider logic into booking logic. Use a PaymentProvider interface and a mock provider now.
Seats are server-authoritative when connected; offline reservations use short-lived local locks and sync with conflict detection.
Tickets must be tamper-evident. Use a signed payload or HMAC in the prototype; never trust QR text alone.
Every important mutation gets an event/audit record: booking, payment, ticket issue, validation, luggage, SOS and settlement.
Never expose secrets in frontend JavaScript, QR codes, or logs.
Use configuration for fares, luggage price, insurance price, commissions and fees. The UI must calculate from config.
Make all payment and booking operations idempotent (safe to retry without creating duplicates).
The app must remain usable when the network disappears. Show a clear Offline/Online indicator.

. Offline architecture
Service Worker caches the application shell.
IndexedDB stores the user's local ticket cache, trip cache, seat state snapshot, and pending sync queue.
SQLite remains the local backend database when the Python server is running.
Every queued mutation gets a client_operation_id so retries are idempotent.
When connectivity returns, sync operations are sent in order where ordering matters.
Server returns accepted/conflict/rejected for each queued operation.
Never silently overwrite a newer booking/seat state during sync.
Show users exactly whether data is live, cached, pending, or stale.
13
. QR security model
A prototype QR should carry a compact signed token, not sensitive personal information. A practical payload is ticket_id + trip_id + seat_id + issued_at + expires_at + version + signature. The driver app verifies the signature locally using a verification key or appropriate shared secret design. The UI then looks up non-sensitive details from the local cache/database. For production, move toward asymmetric signing so verification keys can be distributed without giving every device the ability to issue tickets.

15
. Test checklist before calling it done
Customer can search a route and see available trips.
Customer can select a seat and see the seat ID.
Second customer cannot successfully book the same seat.
Mock payment success creates exactly one booking and one ticket.
Retrying the same operation does not duplicate the booking.
Expired ticket is rejected and expiry is displayed.
Valid ticket is accepted offline when the required verification/cache data exists.
Invalid signature is rejected.
Luggage tag can be registered and scanned.
Trip tracking events appear without page refresh.
SOS creates the correct internal event type and reason.
Offline mode is visible and queued changes synchronize after reconnection.
Operator dashboard updates after booking/payment/ticket events.
Application survives a WebSocket disconnect and reconnects cleanly.
No secrets appear in frontend source or QR payload.

17
. Definition of done
The prototype is done when a user can complete a full local journey from search to seat selection to mock payment to QR ticket, a driver can validate that ticket, the operator can see the trip/revenue state, and tracking/SOS/luggage events can move through WebSockets — including a controlled offline demonstration.
