[Heading 1] 1. Executive brief
[Normal] TURA is an offline-first bus-booking and operations system. The first version should run locally without Mobile Money APIs, while keeping a clean integration boundary so MTN/Airtel payments can be connected later. The browser UI is HTML5/CSS/JavaScript, the backend is Python, and WebSockets carry live seat, trip, tracking, driver, ticket and SOS events.
[Normal] The practical target for today is a polished working prototype, not a production payment deployment.
[Heading 1] 2. Non-negotiable product rules
[List Bullet] Do not hard-code payment-provider logic into booking logic. Use a PaymentProvider interface and a mock provider now.
[List Bullet] Seats are server-authoritative when connected; offline reservations use short-lived local locks and sync with conflict detection.
[List Bullet] Tickets must be tamper-evident. Use a signed payload or HMAC in the prototype; never trust QR text alone.
[List Bullet] Every important mutation gets an event/audit record: booking, payment, ticket issue, validation, luggage, SOS and settlement.
[List Bullet] Never expose secrets in frontend JavaScript, QR codes, or logs.
[List Bullet] Use configuration for fares, luggage price, insurance price, commissions and fees. The UI must calculate from config.
[List Bullet] Make all payment and booking operations idempotent (safe to retry without creating duplicates).
[List Bullet] The app must remain usable when the network disappears. Show a clear Offline/Online indicator.
[Heading 1] 3. Recommended stack
[Normal] Recommendation: choose FastAPI rather than Flask for this project because WebSockets are a first-class requirement. Flask can work with an extension, but FastAPI keeps the realtime architecture cleaner.

[Heading 1] 10. WebSocket design
[Normal] Use WebSockets for state that users need to see change immediately. REST can remain the source for normal CRUD operations.
[Heading 1] 11. Peak features for adding also
[List Bullet] Offline-first PWA: App shell loads without internet; queued actions sync later.
[List Bullet] Signed QR tickets: Stops simple screenshot/text forgery. Add expiry and cancellation checks.
[List Bullet] Offline validation cache: Driver can validate recently issued tickets using a local signed-ticket cache.
[List Bullet] Seat conflict protection: Short seat locks plus WebSocket updates prevent two customers taking the same seat.
[List Bullet] Idempotent payments: Retries do not create duplicate tickets or charges.
[List Bullet] Luggage chain of custody: Every scan changes status: registered → loaded → received/claimed/lost.
[List Bullet] Trip replay: Operator can replay tracking points for a completed trip.
[List Bullet] Operations audit log: Who did what, when, and to which booking/ticket.
[List Bullet] Configurable fee engine: Fare, luggage, insurance and commission values can change without rewriting business logic.
[List Bullet] USSD-ready service boundary: Later add USSD as another client of the same booking/payment services.
[List Bullet] Luganda-ready i18n: Keep labels in translation dictionaries rather than hard-coding text.
[List Bullet] Feature flags: Turn experimental features on/off without deleting code.
[List Bullet] Health dashboard: Show database, WebSocket, sync queue and device status.
[List Bullet] Backup/restore: One-click SQLite backup for the prototype.
[Heading 1] 12. Offline architecture
[List Number] Service Worker caches the application shell.
[List Number] IndexedDB stores the user's local ticket cache, trip cache, seat state snapshot, and pending sync queue.
[List Number] SQLite remains the local backend database when the Python server is running.
[List Number] Every queued mutation gets a client_operation_id so retries are idempotent.
[List Number] When connectivity returns, sync operations are sent in order where ordering matters.
[List Number] Server returns accepted/conflict/rejected for each queued operation.
[List Number] Never silently overwrite a newer booking/seat state during sync.
[List Number] Show users exactly whether data is live, cached, pending, or stale.
[Heading 1] 13. QR security model
[Normal] A prototype QR should carry a compact signed token, not sensitive personal information. A practical payload is ticket_id + trip_id + seat_id + issued_at + expires_at + version + signature. The driver app verifies the signature locally using a verification key or appropriate shared secret design. The UI then looks up non-sensitive details from the local cache/database. For production, move toward asymmetric signing so verification keys can be distributed without giving every device the ability to issue tickets.
[Heading 1] 14. SOS model
[Normal] Do not simulate a real police dispatch as if it happened. The prototype should clearly say 'Demo/Local alert'.
[Heading 1] 15. Test checklist before calling it done
[List Bullet] Customer can search a route and see available trips.
[List Bullet] Customer can select a seat and see the seat ID.
[List Bullet] Second customer cannot successfully book the same seat.
[List Bullet] Mock payment success creates exactly one booking and one ticket.
[List Bullet] Retrying the same operation does not duplicate the booking.
[List Bullet] Expired ticket is rejected and expiry is displayed.
[List Bullet] Valid ticket is accepted offline when the required verification/cache data exists.
[List Bullet] Invalid signature is rejected.
[List Bullet] Luggage tag can be registered and scanned.
[List Bullet] Trip tracking events appear without page refresh.
[List Bullet] SOS creates the correct internal event type and reason.
[List Bullet] Offline mode is visible and queued changes synchronize after reconnection.
[List Bullet] Operator dashboard updates after booking/payment/ticket events.
[List Bullet] Application survives a WebSocket disconnect and reconnects cleanly.
[List Bullet] No secrets appear in frontend source or QR payload.

[Heading 1] 17. Definition of done
[Normal] The prototype is done when a user can complete a full local journey from search to seat selection to mock payment to QR ticket, a driver can validate that ticket, the operator can see the trip/revenue state, and tracking/SOS/luggage events can move through WebSockets — including a controlled offline demonstration.
