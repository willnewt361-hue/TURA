6|Heading 1|'1. Executive brief'
7|Normal|'TURA is an offline-first bus-booking and operations system. The first version should run locally without Mobile Money APIs, while keeping a clean integration boundary so MTN/Airtel payments can be connected later. The browser UI is HTML5/CSS/JavaScript, the backend is Python, and WebSockets carry live seat, trip, tracking, driver, ticket and SOS events.'

10|Heading 1|'2. Non-negotiable product rules'
11|List Bullet|'Do not hard-code payment-provider logic into booking logic. Use a PaymentProvider interface and a mock provider now.'
12|List Bullet|'Seats are server-authoritative when connected; offline reservations use short-lived local locks and sync with conflict detection.'
13|List Bullet|'Tickets must be tamper-evident. Use a signed payload or HMAC in the prototype; never trust QR text alone.'
14|List Bullet|'Every important mutation gets an event/audit record: booking, payment, ticket issue, validation, luggage, SOS and settlement.'
15|List Bullet|'Never expose secrets in frontend JavaScript, QR codes, or logs.'
16|List Bullet|'Use configuration for fares, luggage price, insurance price, commissions and fees. The UI must calculate from config.'
17|List Bullet|'Make all payment and booking operations idempotent (safe to retry without creating duplicates).'
18|List Bullet|'The app must remain usable when the network disappears. Show a clear Offline/Online indicator.'

44|Heading 1|'12. Offline architecture'
45|List Number|'Service Worker caches the application shell.'
46|List Number|"IndexedDB stores the user's local ticket cache, trip cache, seat state snapshot, and pending sync queue."
47|List Number|'SQLite remains the local backend database when the Python server is running.'
48|List Number|'Every queued mutation gets a client_operation_id so retries are idempotent.'
49|List Number|'When connectivity returns, sync operations are sent in order where ordering matters.'
50|List Number|'Server returns accepted/conflict/rejected for each queued operation.'
51|List Number|'Never silently overwrite a newer booking/seat state during sync.'
52|List Number|'Show users exactly whether data is live, cached, pending, or stale.'
53|Heading 1|'13. QR security model'
54|Normal|'A prototype QR should carry a compact signed token, not sensitive personal information. A practical payload is ticket_id + trip_id + seat_id + issued_at + expires_at + version + signature. The driver app verifies the signature locally using a verification key or appropriate shared secret design. The UI then looks up non-sensitive details from the local cache/database. For production, move toward asymmetric signing so verification keys can be distributed without giving every device the ability to issue tickets.'
